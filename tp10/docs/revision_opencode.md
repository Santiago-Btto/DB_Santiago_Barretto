# 3.c - Revisión de scripts con OpenCode Plan

El 04/11/2026 se pidió a OpenCode 1.18.16 (`plan`, `opencode/beam-free`) inventariar scripts SQL, JS, PowerShell y Python de la cursada y revisar TP8/Unidad 6, TP9/Unidad 7 y TP10/Unidad 8. No ejecutó mutaciones. Su respuesta final está en `../evidencia/opencode_revision_respuesta.txt`. Cada decisión siguiente se tomó tras leer el código y la evidencia del laboratorio; no se aceptó la respuesta automáticamente.

| Unidad y hallazgo de IA | Decisión | Comprobación y motivo |
|---|---|---|
| Unidad 8, `run_lab.py`: comparar sólo conteo de pedidos y suma de stock no descubriría un cambio de precio, `activo` o `deleted_at` causado por el semáforo. | **Corregido.** Se añadió un MD5 de precio, stock, actividad y lápida de los cuatro productos del ensayo a la comparación antes/después de cada ejecución. | `evidencia/resultado_laboratorio.txt` registra en C1-C5 idénticos conteos, suma de stock y hash antes/después de cada semáforo. Los hashes cambian solamente entre casos, cuando el servidor de prueba se preparó explícitamente. |
| Unidad 7, `migrar_mongodb.js`: un fallo parcial durante la carga deja la colección creada y el segundo intento se detiene. | **Aceptado como límite de recuperación del TP9; no se borra automáticamente.** Antes de reintentar debe inspeccionarse la colección y decidir manualmente si restaurar una copia o recrear exclusivamente la colección de laboratorio. | El guardia `getCollectionNames().includes('pedidos')` precede la inserción; `tp9/evidencia/20261102_133900/guard_existing_collection.txt` registra el rechazo del segundo intento. La colección verificada conserva 20 documentos. No se ejecutó una falla parcial destructiva sobre la evidencia válida. |
| Unidad 6, `restore_test.ps1`: el uso de la última línea de `psql` podría interpretar mal los avisos; también se sugirió un riesgo de interpolación SQL. | **Descartado para esta ejecución concreta; conservar como hipótesis de endurecimiento.** Los nombres son constantes internas, no entrada del usuario, y las dos consultas reales `SELECT EXISTS` devolvieron una sola línea `t` cada una. | Se ejecutaron ambas consultas en `postgres` y se guardó el resultado en `evidencia/revision_u6_consultas.txt`. El script ya aborta si la base destino existe. Esto no prueba comportamiento para todo aviso posible, pero no justifica alterar un TP anterior sin una falla reproducida. |
| Unidad 8, `run_lab.py`: no admite una segunda corrida sobre la misma base SQLite. | **Aceptado deliberadamente como protección del ensayo.** | El runner falla si el archivo ya existe y exige copia fresca de PostgreSQL. El README indica el procedimiento de reinicio; se evita mezclar estados de dos ensayos o sobrescribir borradores. |

Se descartó además la sospecha de que `SIMULADO_APROBADO` se tratase como venta: `semaforo.sql` sólo actualiza `cola_sync` en SQLite y la verificación observa que `pedido` y el estado de productos PostgreSQL no cambian durante cada corrida. La confirmación real necesitaría una operación de servidor separada, ausente en este TP.
